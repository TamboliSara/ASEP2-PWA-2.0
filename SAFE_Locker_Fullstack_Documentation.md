# SAFE Locker: Full-Stack Architecture & Integration Documentation

This document provides comprehensive technical documentation covering the SAFE (Sustainable Accessible Food Ecosystem) PWA, its split-database backend, hardware integration, operational use cases, and complete data flows.

---

## 1. System Overview

The SAFE system operates as a hybrid PWA (Progressive Web App) integrated with an ESP32-S3 IoT hardware controller. To handle the unique demands of high-frequency hardware telemetry alongside persistent, queryable auditing data, the backend employs a **Split-Database Architecture** on Firebase. 

*   **IoT Real-Time Layer**: Handled by Firebase Realtime Database (RTDB).
*   **Persistent Data Layer**: Handled by Firebase Firestore.
*   **Bridge Layer**: Handled by Firebase Cloud Functions.

---

## 2. Technology Stack

### Frontend (PWA)
*   **Core**: React 18, TypeScript, Vite.
*   **Styling & UI**: Tailwind CSS v4, Radix UI primitives.
*   **Animations**: Framer Motion, GSAP, Tailwind-Animate (high-density "Cyber-Botanical" aesthetic).
*   **Mapping & Charts**: Leaflet (react-leaflet), Chart.js (react-chartjs-2) for Fleet Ops and Kiosk Dashboard.
*   **Hardware Interface**: Web Bluetooth API (BLE).
*   **Offline/Storage**: IndexedDB (via `idb`), standard PWA Service Workers.

### Backend (Firebase)
*   **Firestore**: Persistent Document DB.
*   **Realtime Database (RTDB)**: JSON Tree DB for IoT.
*   **Cloud Functions**: Node.js 18 runtime for business logic and hardware orchestration.
*   **Authentication**: Firebase Anonymous Auth (for seamless kiosk mode).

### Hardware
*   **Microcontroller**: ESP32-S3.
*   **Sensors**: Temperature, Humidity, Pressure, VOC Gas Resistance (e.g., BME688).
*   **Actuators**: Solenoid locks, UV-C sanitation arrays, Ventilation fans.

## 3. Database Architecture (Split-Database)

### A. Realtime Database (RTDB) — The IoT Layer
RTDB handles all live, ephemeral, and high-frequency data states.
*   **`devices/{lockerId}`**: Device registration and metadata (MAC, firmware, bleServiceUuid).
*   **`telemetry/{lockerId}`**: Live sensor readings pushed directly by the ESP32 (Internal/External Temp, Humidity, Gas Resistance).
*   **`status/{lockerId}`**: Live physical state of the hardware (door_state: "open"|"closed", lock_state: "locked"|"unlocked", occupancy: "empty"|"occupied"|"processing").
*   **`commands/{lockerId}`**: Command queue for hardware execution (e.g., `UNLOCK`, `LOCK`, `SANITIZE`). Written by the cloud, read by ESP32.

### B. Firestore — The Persistent Layer
Firestore handles historical data, relationships, and queries.
*   **`donations`**: Records of food assets. Contains donor info, food name, dietary tags, category, and status ("deposited", "retrieved").
*   **`events`**: Audit trail of every system action (e.g., command acknowledgments, manual overrides).
*   **`alerts`**: System anomalies and spoilage alerts generated by sensor fusion (Warnings and Critical Lockdowns).
*   **`sensorSnapshots`**: Historical telemetry logs stored periodically for trend analysis and predictive modeling.

## 4. Backend Cloud Functions

The connective tissue between the PWA, Firestore, and RTDB.

### HTTPS Callables (Invoked by PWA)
1.  **`initiateDeposit`**:
    *   **Trigger**: User confirms food deposit on the PWA.
    *   **Action**: Creates a `donations` document in Firestore with donor metadata -> Writes `UNLOCK` to RTDB `commands/{lockerId}` -> Updates RTDB `status` to "processing".
2.  **`initiateRetrieval`**:
    *   **Trigger**: User slides to retrieve food on the Kiosk.
    *   **Action**: Archives the active `donations` document (status set to "retrieved") -> Writes `UNLOCK` to RTDB `commands`.

### Database Triggers (Automated via RTDB)
1.  **`onTelemetryWrite`** (Triggered when ESP32 updates `telemetry`):
    *   **Action**: Evaluates sensor data against spoilage heuristics (Temp > 8°C, Gas Resistance < 5000Ω).
    *   **If Danger**: Creates an entry in Firestore `alerts`. If critical, sends a quarantine `LOCK` command to RTDB.
    *   **Always**: Copies the current telemetry snapshot into Firestore `sensorSnapshots` for historical auditing.
2.  **`onCommandAck`** (Triggered when ESP32 sets `acknowledged: true` on a command):
    *   **Action**: Reads the executed command -> Creates an immutable audit log in Firestore `events`.

## 5. Hardware-to-Web Integration (BLE)

While Firebase manages cloud sync, local, high-speed pairing is handled via Bluetooth Low Energy (BLE).

*   **Service UUID**: `ec0-0001` (or env configured `4fafc201-1fb5-459e-8fcc-c5c9c331914b`).
*   **Hook Abstraction**: `useLockerController` acts as the API bridge.
*   **Pairing Flow**: The app prompts the user to pair with the ESP32 via the browser's native Web Bluetooth dialog. Once paired, MAC addresses and IDs are registered in RTDB via `registerDevice`.
*   **Fallback**: In the event of an internet outage, critical unlock sequences and sensor evaluations can fall back to direct BLE commands, utilizing local IndexedDB queues until cloud connectivity is restored.

## 6. End-to-End User & Data Flows

### Flow A: Device Setup & Guard Engine
1.  **Boot**: AppShell checks `localStorage` for pairing token.
2.  **Gated Gateway**: If unpaired, route defaults to `/connect`.
3.  **BLE Scan**: User clicks "Connect", browser scans for the SAFE hardware signature.
4.  **Handshake & Cloud Registration**: ESP32 connects -> PWA retrieves MAC -> calls `registerDevice()` to build the RTDB structure (`telemetry`, `status`, `commands`). System unlocked.

### Flow B: Food Deposit (Donor Path)
1.  **Validation**: AppContext checks `occupancyState`. Must be "empty".
2.  **Input**: User enters Food Name, Dietary Tags, and optionally Donor Info.
3.  **Execution**: App calls `initiateDeposit` Cloud Function.
4.  **Hardware Loop**:
    *   Cloud writes `UNLOCK` to RTDB.
    *   ESP32 detects `UNLOCK`, opens solenoid, sets `lock_state` to "unlocked".
    *   User places food, closes door.
    *   ESP32 sets `door_state` to "closed", executes local `SANITIZE` cycle (UV-C).
    *   ESP32 ACKs the command -> Cloud Function `onCommandAck` logs the deposit event.
5.  **UI Switch**: PWA transitions to the real-time Kiosk dashboard.

### Flow C: Quality Intelligence & Spoilage Lockdown
1.  **Monitoring**: ESP32 pushes live `telemetry` to RTDB. Kiosk UI (React) subscribes via `onValue` to animate gauges.
2.  **Quality Index (QI)**: Algorithm calculates freshness. `QI % = (Hours Remaining / Max Shelf Life) * 100` dynamically adjusted by Temp and VOC curves.
3.  **Spoilage Event**:
    *   If Temp > 8°C or VOC Resistance plummets, `onTelemetryWrite` function flags spoilage.
    *   If QI < 30%, function forcefully writes `LOCK` to RTDB `commands`.
    *   Kiosk UI updates `occupancy` state to a **Restricted** state. Standard retrieval UI is hidden.

### Flow D: Fleet Ops (Command Engine / Admin)
1.  **Authentication**: Admin signs in.
2.  **Fleet Map Visualization**: Subscribes to Firestore `donations` and `alerts` to project locker pins geographically via Leaflet.
3.  **Diagnostics Console**: Hooks into real-time RTDB feeds to monitor hardware health.
4.  **Administrative Overrides**: Admin issues a "Force Open" command -> PWA writes directly to RTDB `commands` (bypassing standard checks), triggering a manual solenoid release for cleaning or spoiled food removal.

---

## 7. Key Features & Edge Cases Handled

*   **Zero-Latency Kiosk Updates**: Because the Kiosk dashboard subscribes directly to the RTDB IoT layer, sensor gauges animate in real-time (sub-500ms) alongside the physical hardware.
*   **Cloud-Disconnected Graceful Degradation**: If Wi-Fi fails, the `useLockerController` leverages direct Web Bluetooth writes to actuate the lock and caches the events locally in `idb` for a background sync when connectivity resumes.
*   **Security & Safety First**: The intelligence engine completely prevents end-users from retrieving food computationally determined to be spoiled. It enforces an administrative air-gap.
*   **Complete Auditability**: Through the `events` collection, every single interaction (PWA button clicks, cloud functions, and hardware physical acknowledgments) is recorded. Telemetry PDFs can be generated via `jsPDF` for compliance reporting.
